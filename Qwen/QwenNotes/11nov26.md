## Qwen 2.5-14B P3 first execution

The P3 script was built from the corrected Mistral script and three defects were found and corrected in the audit before any run, then three more surfaced.

### the three failures of the day

**1. Host RAM, before a single step.** `WakeOverlay.full_matrix()` reassembled the matrix with `.detach().float().cpu().clone()`. At 195,888 x 5120 that is three copies of a 3.74 GiB result: 
`.float()` runs on the source device and allocates 3.74 GiB of GPU, `.cpu()` allocates 3.74 GiB of host, and `.clone()` allocates a third. Roughly 7.5 GiB of host RAM on a box with about 12.7 
GiB and a 14B model already resident.

Rewritten to stream in 16,384-row chunks, so the peak is the result plus 335 MiB. The pre-training snapshot is now written in bf16 rather than fp32, which matches the rest of the lineup, because 
Mistral's snapshot is the model weight taken straight off the device and that weight has always been bf16. Every consumer casts to fp32 on load and bf16 to fp32 is exact, so nothing downstream changes, 
and `TARGET_NORM` is now derived the same way on both models. Drive cost halves from 3.74 GiB to 1.87. The write is also local-first now, since `torch.save` straight to Drive FUSE on a file this size is 
the project's most common stall.

**2. CUDA OOM in backward, at step 2.**

```
trainable                         254,853,120
adamw_torch exp_avg + exp_avg_sq  254.85M x 4 x 2 =  2.04 GiB
fp32 gradient                     254.85M x 4     =  1.02 GiB
static after Cell 6                                  9.17 GiB
                                                    ---------
                                                    12.23 GiB
```

Against 14.56 GiB, leaving 2.33 GiB for activations, the SplitHead logit intermediates and fragmentation. The observed failure asked for 502 MiB with 329 MiB free and 255 MiB reserved but unallocated.

Previously thought that a plain fp32 optimiser was affordable here because the overlay confines training to the Wake rows, comparing 224M against the 8B's 706M. That reasoning omitted the optimiser states 
from a budget already at 9.17 GiB. Replaced with an explicitly constructed `bnb.optim.AdamW8bit`, which puts both moments in int8 at 0.47 GiB and saves 1.53 GiB.

Explicit construction rather than `args.optim="adamw_bnb_8bit"`, because on the 8B that string silently resolved to 32-bit AdamW: transformers registers every `nn.Embedding` with bitsandbytes' 
`GlobalOptimManager` for `optim_bits=32` as a stability safeguard, and the overlay is an `nn.Embedding`. The guard checks the object.

### what is confirmed working

```
WakeOverlay: 43824 rows x 5120, fp32, 0.84 GiB
SplitHead: base [0,152064) frozen bf16 + overlay [152064,195888) trainable fp32
  Overlay (Wake rows): 224,378,880
  LoRA: 30,474,240
  Total trainable: 254,853,120
  Frozen full matrix: 1,002,946,560 (torch.bfloat16, not in the optimizer)
  GPU allocated: 9.17 GiB of 14.56 GiB
```

The WakeOverlay and SplitHead architecture executes. Step 0 produces `morph=0.6795`, which matches the permutation null's independently computed `observed L_morph 0.679518` to four decimal places, so the 
differentiable gather through `rows()` and the two-matmul output head agree with the analysis path. `L_repulsion` reads exactly 0.0 as expected at this Wake-to-Wake cosine. The step-0 losses are 
byte-identical across the optimiser change, so the forward is deterministic.

**More sharply: `un-` is significant on Qwen at z = −6.1, and on Mistral it was null in the wrong direction** (z = +1.08, excess −0.021, meaning its directions agreed with each other less than permuted

Held with appropriate caution. The two models tokenise differently, so the supervision sets are not the same pairs: Qwen resolves 1,234 where Mistral resolves 1,413, Qwen's `-ion` holds 40 pairs where 
Mistral's holds 69, and the base-vocabulary norm differs by a factor of seven (1.1406 against 0.1678). The Latinate concentration reported from Mistral is not reproduced in this form on Qwen, and whether 
that is a property of the model or of its tokenisation is not yet separable.

2,151 of 43,824 against Mistral's 2,261 of 44,553, so 4.9% against 5.1%. The twentyfold dilution argument transfers directly, and the treated-versus-control contrast rather than aggregate isotropy will

## pre-registration

Recorded before the run produces a single trained step.

Mistral ran P3 because it was the only model in the lineup whose Wake region sat below the 0.998 isotropy attractor, at 0.995, with the largest embedding reorganisation in the set (drift cosine 0.485). 
The reasoning was that there was structure there to move. Qwen's P1 canonical sits at the attractor.

So:

1. **If the morpheme effect requires pre-existing structure, Qwen should move less than Mistral's +0.0708.** It starts lower (+0.0301 against +0.0458) and sits at the attractor rather than below it.
2. **If it moves comparably, the pre-existing-structure account weakens considerably**, and the effect is better described as something the objective can manufacture anywhere. Mistral's own per-group result already points this way: fourteen of its fifteen largest gainers were not significant beforehand, two of them worse than chance.
3. **L_device should not move.** It reads 0.1873 to 0.2145 across the step-0 micro-batches against a margin of 0.2000, which is where it sits in every run of the project and is the value the loss takes when its categories carry no information.
4. **The LM term starts far higher than Mistral's**, 5.0 to 6.6 against roughly 3.8, consistent with P2 having floored at 5.9209 rather than 4.705. Any comparison of P3's language-modelling cost across the two models has to be made against each model's own P2 minimum, not in absolute nats.
